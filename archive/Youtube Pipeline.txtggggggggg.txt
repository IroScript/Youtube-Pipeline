  4. CURRENT REMAINING PROOF GAPS
  ===============================

  The remaining work is primarily REAL-WORLD runtime proof.

  A. CONCURRENT DUPLICATE EXECUTION

  Current test proves:

  Request 1 → allowed
  Request 2 → blocked
  clear → allowed

  But this was sequential.

  You MUST test simultaneous requests.

  Use real parallel HTTP clients, threads, or async execution.

  Scenario:

  Two or more requests simultaneously attempt to generate the SAME stage for the SAME idea.

  Expected:

  * Exactly one request obtains the generation lock/job.
  * Other requests are rejected safely.
  * Only one active job exists.
  * No duplicate generation record is created.
  * No corrupted state occurs.
  * No duplicate output is created.
  * After the job is cleared/completed, a new request is allowed.

  If the implementation is not race-safe, fix only the minimum necessary code.

  Add a permanent regression test.

  ---

  B. REAL PROCESS CRASH RECOVERY

  The existing crash test is state simulation.

  That is NOT enough.

  Perform a real crash scenario if the environment permits:

  1. Start application.
  2. Start real pipeline execution.
  3. Allow it to enter an in-flight state.
  4. Kill the actual Python/application process.
  5. Restart application.
  6. Run recovery.
  7. Detect orphan/in-flight execution.
  8. Restore safe state.
  9. Clear/reconcile active job.
  10. Ensure pipeline can continue safely.
  11. Ensure the same stage is not executed twice incorrectly.
  12. Verify recovery is idempotent.

  If real process killing cannot safely be automated in the current environment, document:

  REAL CRASH TEST = BLOCKED BY ENVIRONMENT

  Do NOT call the simulated test equivalent to real crash proof.

  ---

  C. LIVE PAUSE / RESUME

  Current state-level/dry-run pause testing is not sufficient.

  Perform a real test:

  1. Start an actual pipeline execution.
  2. Wait until a real stage is executing.
  3. Issue pause.
  4. Verify the pipeline does not start another stage.
  5. Verify state becomes PAUSED.
  6. Verify active execution is handled safely.
  7. Issue resume.
  8. Verify execution continues from the correct point.
  9. Verify no duplicate stage execution.
  10. Verify final state.

  If live pause cannot be tested safely, report it as NOT PROVEN.

  ---

  D. RETRY STABILITY

  This is a PRIMARY requirement.

  Test every retryable failure path that belongs to the production pipeline:

  * Prompt failure
  * SEO failure
  * Video failure
  * Upload/package failure if applicable

  For each:

  1. Force a controlled failure.
  2. Verify failure state.
  3. Verify failure reason is recorded.
  4. Verify retry is allowed.
  5. Retry.
  6. Verify active job handling.
  7. Verify retry count.
  8. Verify successful recovery.
  9. Verify no duplicate output.
  10. Verify final state.

  Also test retry-limit behavior.

  Expected:

  retry count cannot exceed MAX_RETRIES.

  After retry exhaustion, the system must enter the defined terminal/permanent failure behavior.

  Do not silently retry forever.

  ---

  E. SEQUENTIAL MULTI-ROW EXECUTION

  Test real execution across multiple ideas.

  Example:

  Idea A → execute
  Idea B → execute
  Idea C → execute

  Verify:

  * correct next target selection
  * completed rows are skipped
  * incomplete rows are selected
  * failed rows follow retry rules
  * one row does not corrupt another row
  * no duplicate execution
  * correct state transitions
  * correct final verification

  This must be real execution, not only dry-run.

  * SEO exists

  * Video file exists
  * Package exists
  * Required metadata exists
  * Verification flags are correct
  * missing_fields = empty
  * final state = COMPLETE

  One missing required field must prevent completion.
